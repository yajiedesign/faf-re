# AGENTS.md —— wmdiff 配对 harness

本文件是 `dependencies/WildMagic3p8/wmdiff` 以及它背后的重建配对工作的 agent 操作指引。
**仓库级的约定**（构建入口、部署、机器环境、术语、Go/mpemu 工具链）在仓库根目录的
`AGENTS.md`；**逐行的完整记档**在同目录的 `README.md` —— 那是这个 harness 的账本，
每加一个比对项、每撤回一个结论都要在那里写清楚（含地址、调用约定、字宽、变异计数）。

动手前先读：本文件 → `README.md` 的 `## Rules` → 根目录 `AGENTS.md` 的构建/部署两节。

## 它是什么

一个**独立的 32 位控制台工具**：把零售二进制 `ForgedAlliance_6c6c92f.exe`
（`C:/ProgramData/FAForever/bin/`，映射在 `0x00400000`，WM3 库代码在
`0x00A3xxxx`-`0x00A7xxxx`）映射进自己的地址空间，与重建版**逐位**比对同一批输入。
它不碰 `main.vcxproj`，也不改任何 `.vcxproj`。

## 配对工作的第一步：可达性判定（三轮 + 三态）

**在给任何函数/类写比对项之前，先按 `reachability-rules.md` 把它判成 `executed`。**
链接探针只回答"有没有被链接"，**不回答"`src/` 到不到得了"** —— 这两个答案在 hull 类和
`Eigen` 上是**相反的** ✓

**三轮**（由粗到细，每轮都能否掉一批）：

| 轮 | 做什么 | 挡掉什么 |
|---|---|---|
| **0** | 注释掉某精度的全部 `template WM3_ITEM class X<T>;`，重编 `main.vcxproj` | 整精度没人引用 ⇒ 出局。**只作初筛，结论不可直接用** |
| **1** | 打开点名的 `.obj`，读**调用点那一行的实参静态类型** | "看着用 double、其实调用点给的是 `float`" |
| **2** | **向上追调用链直到 `src/`** | **"被链接但 `src/` 到不了"** |
| **3** | 读**上下文若干行**（声明、`if constexpr`、`typedef`、分支是否可达） | 只看一行造成的误判 |

**三态**：`executed`（进配对队列）/ `linked-but-unreachable`（记录、不排期）/ `not-linked`（出局）。

**两条铁律**：

1. **模板实例化由调用处的实参类型决定** —— `Wm3::ContAlignedBox(8, vertices)` 里
   `vertices` 是 `Wm3::Vector3f[8]` ⇒ **只实例化 `float`** ⇒ ⇒ 我此前就是漏了这一步，
   才把 `ContAlignedBox` 当成"通用" ✓
2. **`double` 一律默认可疑** —— 目前**没有任何一处 `src/` 调用点给出 `double` 实参** ⇒
   看到"实参是 `Real`"时**默认按 `float`**，除非能**指出 `src/` 里给 `double` 实参的那一行** ✓

**这次审计的实际结论（2026-10-28，见 `reachable.md`）**：

* `Eigen<float>`、`Eigen<double>`：**`linked-but-unreachable`** ⇒ ⇒ 链在 `ContOrientedBox` →
  `EllipseFit2`/`EllipsoidFit3`/`ContEllipse`/… 处断（那些函数**没有任何调用者**）；
  而 `src/` 唯一的 containment 调用是 `ContAlignedBox(8, vertices)`（`float`），
  **`ContAlignedBox` 自己算极值、不调 `GaussPointsFit`** ⇒ ⇒ **两条路在同一个文件里就分开了** ✓
* 三个 hull 类（**float 和 double 都一样**）：**`linked-but-unreachable`** ⇒ ⇒ 链断在
  `ContMinBox`（唯一调用者是它自己的递归）✓
* 十六个 float 类 + `Vector3::Normalize` + `Vec3::Dot/Cross/LengthSq`：**`executed`**，
  每个都有引用的 `src/` 调用点与实参类型 ✓

⇒ ⇒ **判定的执行者必须是 sub agent**：它要开 `.obj`、逐级追链、读上下文，是一次独立调查 ⇒
⇒ 派活时要求**每个结论都引用那一行源码**，只给结论不给引用的不采纳 ✓

## 只有引擎真的会执行的实例化才值得配对

**`double` 一律默认可疑**：`src/` 里没有任何一行给 Wild Magic 模板传 `double`，因此本表里
47 个 double 比对项全部 `dead`（逐项证据在 `double-audit.md`）。harness 默认跳过它们，
`--include-dead` 才跑；删行会丢掉已验证的数据，所以行保留、默认不参与判定。


**这是本 harness 的范围规则，先读它再读别处。** 库里 `float`/`double` 各写了 **140 个**
显式实例化，但 `src/` 真正引用的只有 **float 20 个、double 4 个** ⇒ ⇒ 给引擎不用的实例化
配对**改不了引擎**，那不是工作。

**判定方法（不用 `grep`，也不用 `static_assert`）：**

1. 把某个实例化的**全部** `template WM3_ITEM class X<T>;` 一次撤掉；
2. 重新构建 `main.vcxproj`；
3. **链接通过** ⇒ 引擎不引用它；**链接失败** ⇒ 未解析符号**直接点名**被引用的成员。

> `grep` 类名会误报（头文件、注释、库自己的显式实例化都会命中）。
> 类里的 `static_assert` 也不行：库写了显式实例化，**assert 无论引擎用不用都会触发**
> （`IntrBox3Sphere3<double>` 就是这么被误判过一次）。

**判定的结果（2026-10-27，`reachable.md` 为准）：**

| | 总数 | 引擎引用 | 结论 |
|---|---:|---|---|
| double | 140 | **4**：`Eigen`、`ConvexHull`、`ConvexHull2`、`ConvexHull3` | 其余 **136 个** ⇒ **不再配对** |
| float | 140 | **20**（`Vector3` 90 符号、`Box3` 34、`Eigen` 32、`Sphere3` 26…）| 其余 **120 个** ⇒ **不再配对** |

⇒ **已入表的比对项不撤**：它们逐位验证过、跑起来不花钱，而且 x87 方法就是从它们身上建立的。
⇒ 停的是**继续往未使用实例化上投工作**。
⇒ **上面那张"引擎引用"表是第 0 轮链接探测的产物，不能当判定。** 它回答的是"链接
器是否需要这个符号"，而对**头文件内联模板**这个回答是两义的：删掉库里的显式实例化，引擎
自己的 TU 会实例化它要用的那份，链接照样成功 —— 这既可能是"没人用"，也可能是"人人都在
用"。`Wm3::Quaternion<float>` 就是后者：引擎在 `CAimManipulator.cpp:1076`（`Identity()`）、
`CUnitMotion.cpp:813-816`（读四个分量）、`CAiFormationInstance.cpp:3585`（`operator==`）、
`CollisionBeamEntity.cpp:71-73`（`Rotate`）都在用它，探测却报告"未引用" ✓

⇒ ⇒ **第 0 轮只能用来筛候选，不能用来结案。** 内联模板类的每个成员必须按 `src/` 的
调用点逐条判，而且**"类被执行"不等于"这个成员被执行"** ✓

⇒ ⇒ 真实状态（`reachable.md` 为准）：**219 个 WM3 函数** = 72 已配对 + 42 未匹配 + 105 不适用
（0 失败）。42 里 **28 个是可配对的**（引擎调用 + 零售有独立体），14 个是**零售体尚未查清** ✓

⇒ ⇒ `Eigen`、`ConvexHull`/`2`/`3`（两个精度）确实是 `linked-but-unreachable`：链断在
`ContMinBox`（唯一调用者是它自己的递归）、`ContEllipse`/`ContEllipsoid`/`ContLozenge`、
`EllipseFit2`/`EllipsoidFit3`/`CircleFit2`/`SphereFit3`/`OrthogonalLineFit2/3`/
`OrthogonalPlaneFit3`；`src/` 里唯一的 containment 调用是 `ContAlignedBox(8, vertices)`，
实参是 `Wm3::Vector3f vertices[8]` ⇒ 只有 float ✓

## 构建与运行

```bash
# 构建 harness（从仓库根目录）——它是引擎 CMake 工程的一个 target，
# 用 clang-cl x86 + faf_codegen + faf_wm3_build_flags，与引擎同编译器同开关。
cmake --preset clang-x86-release
cmake --build --preset clang-x86-release --target wmdiff
# -> build/clang-x86-release/tools/wmdiff/wmdiff.exe

# 运行
./build/clang-x86-release/tools/wmdiff/wmdiff.exe --list
./build/clang-x86-release/tools/wmdiff/wmdiff.exe --iters 1000000 --seed 0x5EED2007
./build/clang-x86-release/tools/wmdiff/wmdiff.exe --iters 1000000 --seed 0xA5A5A5A5 --filter "IntrBox2Box2"
```

**依赖树的一次性准备**：`dependencies/WildMagic3p8` 是上游子模块，先应用
`dependencies/patches/wildmagic3p8_faf_required.patch`，再应用
`dependencies/patches/wildmagic3p8_wmdiff_access.patch`（只把两个 `CompareArrays`
改成 public，对代码生成无影响）。

`--filter` 是逗号分隔的子串匹配；`--max-mismatch N` 限制打印条数；`--cw` 指定 x87 控制字
（默认 `0x007F`，即引擎的 `_PC_24`，**不要改**）。

**收官判据：全表 × 五个种子 × 1,000,000**（`0x5EED2007`、`0xDEADBEEF`、`0x12345678`、
`0xC0FFEE01`、`0xA5A5A5A5`）。单种子 × 百万**不是**门 —— 一个 10⁻⁶ 的差异需要
~5×10⁶ 次抽样才有像样的机会露面。

## 教训

这些是比"又多了几个比对项"更耐久的部分。每条都对应一次实际踩坑。

### 参照系是 WM3.4 副本，不是 WM4 SDK

wm3.8 重建版整体是从 Wild Magic 4 译来的，所以**拿 WM4 派生的函数去比 WM4，只能证明翻译忠实，证不出翻译漏了特性**。判定"这个函数零售是什么样"时，去 `.tmp/wm3/Source/` 找同名函数；只有在 WM3.4 副本里没有对应物时，才转向零售二进制。

已因此找回两处回退（都发生在 wm3.8 重建版里，都曾被当成"引擎无关紧要"）：`ContAlignedBox` 相对 WM3.4 少了**掩码参数、盒子的初始化、"无有效点"约定**三项；`bSolid` 参数同理。

⇒ ⇒ **副本的第二个用途：当阅读路线图，省掉大部分机器码。** 读一个零售的 `double` 体时，**先看 WM3.4 副本的同名函数**，得到分支表（有哪几种情形、什么顺序、每支算哪些量）；然后**只读那些情形对应的基本块**，把 retail 的分组与次序对上去 ⇒ ⇒ 不要一上手就对整段体做符号执行/路径枚举：`IntrLine3Capsule3<double>::Find`（`0x00A80080`）的数百分支路径枚举了大半天仍未收敛，而按副本的骨架读，六种情形是逐块可读完的 ✓

⇒ ⇒ 顺序因此改为：**副本给骨架 → 逐块读零售 → 立即转写 → 比对项验证**；"逐路径符号展开"只在副本也给不出结构时（例如整个函数在副本里不存在）才考虑 ✓

### 一致性模式只有一种，就是主项目重建版用的那种

`main.vcxproj` 用 `/permissive-`，**wm3.8 重建版的 `Foundation.vcxproj` 现在也用 `/permissive-`**，harness 同样。理由很直接：最终只有一个二进制，混用模式没有意义。代价是 WM4 译来的文本里有对**依赖基类**成员的未限定调用，严格模式拒收（MSVC C3861）——逐处显式限定基类即可，**行为不变**（同一个函数、同样的参数）。

### harness 编译被测代码的方式，必须与引擎编译它的方式一致

否则 harness 测的是另一个程序，而不是引擎构建的那个。一次编译只有一个开关，所以**树与 harness 必须统一到同一模式**，不能各行其是。

### "比对项失败"先分清三类：重建的错、量具的错、两者叠加

量具侧的 ABI 错误会**伪装成重建的数值差异**。实例：零售的 `ContAlignedBox` 有第四个栈参（掩码指针），引擎的调用点恒传 `0`；harness 少压一个 → 第四格是垃圾指针 → 零售走进掩码路径 → 看起来"重建算错了一半的点"。**重建其实一直是对的。**

同类第二例（swept double 比对项"恒返回 0"）：harness 给四个 double 体的 naked thunk 结尾写成 `fstp qword ptr [esp+40]` ⇒ 把返回值存进了**调用者的出参指针槽**（存指针的那一格），而不是存进指针指向的那个 double ⇒ ⇒ 比对项于是拿重建的答案去比**自己那个仍是 `0.0` 的局部变量** ⇒ ⇒ 看着像"零售恒返回 0"，其实零售一直是对的（正确答案 1 时它就返回 1）⇒ ⇒ **"这个比对项恒返回 0"更可能是"这个比对项根本没收到答案"，而不是"零售恒返回 0"** ⇒ ⇒ 最便宜的查法：**看这个比对项到底收到了什么**（把比对项收到的字节打出来），别急着改重建。

### 零售的调用点能直接定死被调函数的签名

数零售调用点压了几个参数、压了什么，就知道被调函数有几个参数、默认值是什么。`push 0` 说明第三参有默认值 `= 0`——这正是"引擎调用点无需改动"的依据。

### 私有静态/成员要用显式实例化去取

MSVC 把访问权限编进符号名，跨 TU 的引用**不会**绑到类自己 `.cpp` 发射的那个实例化。用显式实例化（"Rob" 惯用法）取私有地址，命中的是引擎自己的代码而非副本。`#define private public` 不行：它改掉修饰名，链接直接失败。

### cdecl thunk 必须自行回收替零售压入的参数

否则 thunk 自己的 `RET` 跳回参数中间，故障地址恰是某个参数值，看上去极像跳进了 CRT 的 math-error 路径——其实只是栈差了固定字节数。

### 比对项要覆盖退化分支，也要证明它有区分力

随机几何走不到判别式为零、恰好相切、"已经相交"这类分支，生成器必须**精确构造**它们（半径取 2 的幂，`R*R` 与 `|D|²` 是同一个数，减法精确）。另外要**变异测试**：单侧交换参数或扰动输出，比对项必须失败，否则它可能恒等比较。

### 判定差异归属的顺序

先读零售函数体 → 再交叉核对 WM3.4 副本 → 才动重建源码。三步都做过之后仍说不清，才叫"机制不明"。

⇒ ⇒ **顺序反过来更省时**：`IntrLine3Capsule3<double>::Find`（`0x00A80080`）的体有**数百条符号路径**，一次"逐路径符号枚举"烧掉大半天仍未收敛（`paths2.txt` 18 MB，绝大多数格还是 `?`）⇒ ⇒ 正确做法是**先拿 WM3.4 副本当阅读路线图**：它给出"有哪些分支、什么顺序、每支算什么"，于是只需读**它走得到的那些基本块**，而不是把整个控制流图展开 ⇒ ⇒ 读完一个块就转写一个块，**边读边落** ✓

⇒ ⇒ 判据（决定要不要上"重工具"）：**这次要读的是"哪几块"，还是"全部分支"？** 前者用副本当骨架 + 逐块读；后者才需要符号执行/路径枚举 —— 而后者在零售这种体积的体上**基本不收敛**，不该作为默认手段 ✓

⇒ ⇒ ⇒ 与"参照系是 WM3.4 副本"那条合起来：副本的价值**不只是**"判定谁对"，更是**减少要读的机器码**。上面那次如果一开始就查副本，`0x00A80080` 的六种情形（柱面、上下半球、平行支、切根……）本来是一眼就有的结构 ✓


### 槽位表要从基类自己的 vftable 读，不要从派生类反推

零售 `Distance` 基类的槽位表曾被读错两处：`+0x04` 被当成"第二个析构函数"（实际是基类的窗口搜索 `Get`），`+0x10` 被当成"基类泛型三参 `GetSquared`"（零售**根本没有**这个成员）。一个误读连带造出"零售七个虚函数、重建八个"的错账——其实两边都是八个，只是**声明顺序不同**。

正确做法：基类构造函数写入的 vptr 指向**基类自己的** vftable，从那里读槽位，再与派生类的 vtable 对照（派生类只覆盖一部分槽）。派生类的 vtable 不能用来推断基类的虚函数集合。

⇒ ⇒ **还要按"实例化"分别读**：同一个类的 **float 与 double 两个 vftable 不对齐** —— 例：`IntrBox2Circle2` 的 float vftable 是 `0x00D71EC0`、double 是 `0x00D71EDC`，而 float 的 `Test` 在它的 **+0x0C**、double 的 `Test` 在它的 **+0x08**（double 的基类少四个入口）⇒ ⇒ ⇒ **一个槽号在另一个实例化里指的是另一个槽** ⇒ ⇒ ⇒ 所以每个地址都要从**那个实例化自己的** vtable 读，**不能拿另一个实例化的槽号套用**。

⇒ ⇒ **基类体是跨类共享的**：`Intersector` 的 `0x00A455A0`/`0x00A455D0` 被两个 2D 类共用、`0x00A45630`/`0x00A45650` 被五个 3D 类共用 ⇒ ⇒ ⇒ 同一段零售代码只做一遍，多处受益 ⇒ ⇒ ⇒ 反过来，**读基类槽位时先问"这个体被几个类共用"** ⇒ ⇒ 免得把同一段代码当成几段分别处理。

### 上游两个版本写法一致，不构成零售一致的证据

零售的 `Distance` 基类与 WM3.4 副本、WM4 SDK **虚函数集合相同、声明顺序不同**（零售把两个窗口搜索放在 +0x04 与 +0x10，重建放在最后）。也就是说，"翻译忠实"与"两个上游一致"都推不出"二进制相同"——这正是 wmdiff 存在的理由。反过来，零售与上游不一致时以零售为准（判定标准是与零售逐位一致），WM3.4 副本只用来解释零售偏离在哪。

### x87 条件码的极性要用仓库自己的模拟器定案

`fnstsw` 的状态字里 **C0 在 bit 8、C2 在 bit 10、C3 在 bit 14**（`tools/x87sim/x87sim/machine.py`），而 x87 比较的标志位按 **ST(0) ? ST(i)** 编码：**C0 = 1 表示 ST(0) 小于 ST(i)**，不是"大于"。凭直觉读会把 `test ah,0x41` + `je` 的极性读反——读反了就会断言"零售的 `SetDifferenceStep` 把正参数存成 1e-3"，而实测恰好相反（零售与两个上游文本一致）。

定案手段有三层，按代价从低到高：先读模拟器的 `_compare`（`c0 = 1 if a < b else 0`）与 `decode.py` 里 `fcom st(i)` 的比较方向；再用 `tools/x87sim/hwprobe` 在真机上跑那几条指令量状态字；**最后由比对项实测确认**——把重建侧写成反的，比对项必须失败（如 160086/200000 失配）。反汇编的读法只是候选，不是结论。

⇒ ⇒ **"模拟器是权威"说的是它的解码与算术模型，不是它对任意零售体的执行**。零售体里那个 `fnstsw ax; test ah, imm; jcc` 惯用法（`TEST` 只把 x87 码变成整数标志，**不改变条件极性** ⇒ ⇒ `test ah,1; jne` = "C0 置位"、`test ah,0x41; jae` = x87 的"大于等于"）⇒ ⇒ 模拟器在这种体上会给出错误结果（曾对 `DistSegment3Segment3` 的 trivial 输入返回 NaN）⇒ ⇒ ⇒ 所以：**读体靠模拟器的解码器，定极性靠 hwprobe，裁决靠比对项实测**；模拟器跑某个体得出的结论，先确认它能正确执行那个体。

⇒ ⇒ **比较的方向是同一个，不随编码变**：`FCOM`/`FCOMP`/`FCOMPP` **都是比 ST(0) 与另一个操作数**（`FCOMPP` 的那个固定是 ST(1)），**C0=1 ⇒ ST(0) < 另一操作数** ⇒ ⇒ 真机探针定案（`ST0=1.0, ST1=2.0` ⇒ 三者都 C0=1 ✓），Intel SDM 的伪码也是这个方向 ✓ ⇒ ⇒ ⇒ **曾把 `FCOMPP` 记成"比 ST(1) 与 ST(0)"（即方向相反），那是错的，已撤回** —— 当时的"证据"（零售 `Distance::Get` 的 `fldz; fcompp` 在 `fDF0<0` 时继续）其实同样只支持正确方向 ✓

⇒ ⇒ ⇒ 另两条读体的坑：**capstone 把 `D8 D0+i` 印成 `fcomp`，但它是 `FCOM`（不弹栈）** ⇒ ⇒ 字节才是权威（reg 域 2=FCOM、3=FCOMP）⇒ ⇒ 按"会弹栈"去追 x87 栈会把整条 trace 算错；以及 `test ah,0x41` 之后的 `jp` 是 x87 的**"大于或无序"**（PF 是 AND 结果的**偶校验** ⇒ ⇒ C0 与 C3 一致时跳），`test ah,5` 之后的 `jp` 是"C0 == C2" ✓

### 重建跑在 `_PC_24` 下，所以 `double` 也不是 binary64

引擎把 x87 控制字设成 `_PC_24`（`fninit; fldcw 0x007F`）⇒ **x87 的有效位是 24 位、指数是扩展的** ⇒ ⇒ 零售的 `double` 路径**不是 binary64** ⇒ ⇒ 重建里任何写成普通 C++ `double` 算术的地方都可能与零售不同。

例证：`0.5/1e-3` 在 binary64 是 `500.00000000000006`，在 x87 上是**精确的 `500.0`** —— 而零售的构造器存的正是 `500.0`；`FSQRT` 在 `_PC_24` 下也是 24 位的，binary64 的 sqrt 与它在 **85% 的输入上**不同。

⇒ 修法是**内联 x87**（`Wm3Detail::X87Add/Sub/Mul/Div/Neg/Abs/Sqrt`），只用在 `double` 分支，`float` 分支一字不动。⇒ 这条只影响**重建与零售的逐位一致**，不影响引擎行为（引擎是纯 float）⇒ 但它让"零售的 double 路径"这件事**第一次可测**。

⇒ 同时说明：`fnstsw` 之后**控制字会被重新规范化，但三位精度位被保留**（零售里的 `AND EDX,0x300 / OR EDX,0x7F`）⇒ ⇒ 看到 `fldcw` 不等于"退回 53 位" ⇒ ⇒ 读分支极性时按这个前提算。

⇒ 再一条反直觉的：**装载不按 RC 精度舍入，只有运算结果舍入**。`_PC_24` 下 `FLD` 一个 64 位 double、或把 64 位内存当操作数，**都不舍入**（寄存器本来就是 64 位有效位，装得下 53 位）⇒ ⇒ 一次运算才舍入一次到 24 位 ⇒ ⇒ ⇒ 所以建模时**不能在装载/构造时舍入**：实测把建模值在构造时舍入到 24 位，`DistSegment3Segment3<double>` 的失配从 **1% 涨到 75%** ⇒ ⇒ 判据：**harness 比对项实测**。

⇒ 还有一条，但要**按类分别定**：`double` 分支**能不能只换类型**，取决于零售那个类的 double 体是不是它 float 体的同一写法。`DistLine3Segment3` 的 double 体（`0x00A81330`）**就是**它 float 体（`0x00A80DE0`）的同一算法、同一分组 ⇒ ⇒ 换成 x87 建模即可（但分组仍要从指令里读出来）；而 `DistSegment3Segment3` 的 double 体**也是**它 float 体（`0x00A7E660`）的同一算法 —— 这点曾误判为"差 1%、差在 side/corner 分组"，见下一条 ⇒ ⇒ 判据始终是 **harness 实测**，不是"看起来像同一个算法" ⇒ ⇒ 这与"翻译忠实"是两件事：翻译忠实 ≠ 与零售逐位一致。

⇒ ⇒ 再加一条更根因的：**软件模型本身会"双重舍入"**。`Wm3Detail::X87` 用 `double` 存值、每个运算舍入一次 —— 但**两个 53 位操作数的乘积需要 106 位**，先舍到 binary64、再舍到 24 位 = **舍了两次**，得到的是另一个数 ⇒ ⇒ 所以 `DistSegment3Segment3<double>` 的 "20/2000 失配、散布所有区域"**不是**结合方式问题（十二变体搜索纹丝不动正因为那个自由度不存在），而是**这个二次舍入** ⇒ ⇒ 修法是 `Wm3Detail::X87Asm`：**直接在硬件 x87 上算**的值类型（`Foundation/Math/Wm3Vector3.h`）⇒ ⇒ 判据仍是 harness 实测：四个比对项退回 binary64 后各失配 199845/199839/199839/199837 of 200000 ✓

⇒ ⇒ ⇒ **推论（省时间的那条）**：当"把所有看起来可能的自由度都搜过、失配数一个都不动"时 ⇒ ⇒ **别再搜了**，去查**模型本身的保真度**（精度、舍入次数、指数范围）—— 自由度不存在时，搜索永远收敛到同一个数 ✓

⇒ ⇒ 关于 `tools/x87sim`：**它的解码器是权威**（读零售体靠它），**它的算术模型可用**（舍入规则），但**它的"执行"对某些零售体不可信** ⇒ ⇒ 零售体用 `fnstsw ax; test ah, imm; jcc` 这个惯用法，而 **`TEST` 只是把 x87 码变成整数标志，不改变条件的极性** ⇒ ⇒ `test ah,1; jne` = "C0 置位"，`test ah,0x41; jae` = x87 的"大于等于" ⇒ ⇒ 按整数分支去读会把整个区域读反 ⇒ ⇒ 而模拟器在这种体上会给出错误结果（曾对 `DistSegment3Segment3` 的 trivial 输入返回 NaN ⇒ ⇒ 据此得出的"110/300 抽样不一致"**已撤回**）⇒ ⇒ ⇒ 教训：**模拟器跑零售体得到的结论，先确认它能正确执行那个体**；执行不了就用 **harness 比对项实测** ⇒ ⇒ 模拟器的**硬件探针**（hwprobe）仍然是条件码极性的权威（它量的是真机）。

### 判定标准是"与零售逐位一致"，不是"与数学答案一致"

**是不是 bug 不好说**（零售那侧的行为也许是被别处的 bug 造出来的）；**但目前阶段就算是 bug 也要复现它** ⇒ ⇒ 重建照抄零售的行为，**在相关函数的注释里**记档（零售的行为是什么、证据是什么、为什么照抄）⇒ ⇒ **比对项留在比对表里**，不写成"重建与零售不一致"的待办 ⇒ ⇒ 收敛位置只有两个：重建源码，或比对中零售一侧的接线；**绝不在"怎么编译"上，也绝不在"把比对项拿掉"上**。

⇒ 前提：**先确认量具没坏**（见"比对项失败先分清三类"那条）⇒ ⇒ 一个比对项"恒返回 0"曾被当成零售的缺陷记了整整两轮，实际是 harness 的 thunk 把返回值存进了**出参指针槽** ⇒ ⇒ 零售一直是对的 ⇒ ⇒ ⇒ 所以下"重建照抄"这个结论之前，量具要查一遍。

### 比 `bool` 的比对项只是"弱见证"，不是"看不见"

一个比对项如果返回 `bool`（`Test`/`Contains` 这类），24 位与 binary64 的差别**只在值落到阈值的一个 ulp 以内时才翻转布尔** ⇒ ⇒ 抽样里出现率约 **百万分之一** ⇒ ⇒ 所以：

* 它**通过**百万次抽样，**不能**证明底下的算术对 ⇒ ⇒ 只是"没撞上"；
* 它**失败**一次，**就是**真失配 ⇒ ⇒ 不能因为"绝大多数都过"就当噪声。

实例：七个 `Intr*<double>::Test` 比对项在默认种子上 1,000,000/1,000,000 全过，于是被记为"无需改源码"；换到第五个种子 `0xA5A5A5A5`，`IntrBox2Box2<double>::Test` **百万分之一**失配（零售 true、重建 false，输入是极端量级）⇒ ⇒ 那七个体的 double 分支**确实需要** x87 转写 ✓

⇒ ⇒ **收官判据是"全表 × 五个种子 × 1,000,000"，不是"默认种子 × 1,000,000"** ⇒ ⇒ 种子是 `--seed` 给的，换种子就是换输入序列 ⇒ ⇒ 一个 10⁻⁶ 的差异需要 ~5×10⁶ 次抽样才有像样的机会露面 ✓

⇒ 推论：**bool 比对项不能当作"算术已对齐"的证据**；要证算术，用**返回值**的比对项（`Get`/`GetSquared`/参数）。反过来，bool 比对项适合证**分支/分类**对不对，不适合证**数值**对不对。

### harness 自己的两个盲点：旧二进制、重复的比对项

比对表有两个**与重建无关、却会伪装成重建差异**的坑：

1. **构建失败时 harness 会跑旧二进制。** `build_wm3.bat` 把错误写进自己的日志和退出码，而比对项照测 `wmdiff/build/` 里那个**上一次成功构建**留下的 exe ⇒ ⇒ 于是"改了源码、结果一个数都没变"会被读成"这个改动不影响结果" ⇒ ⇒ **信比对项之前先看构建退出码 + exe 的时间戳** ⇒ ⇒ 一次十二变体的搜索就是这么白跑的（每个变体都"无变化"，因为根本没重编）。
2. **变体搜索会把重复的比对项留在表里，而种子按比对项在表里的序号派生。** 同一批四个比对项被追加了三遍 ⇒ ⇒ 后面每个比对项的种子都被顶掉 ⇒ ⇒ 表看起来"比对项数变多、结果都对"，实则**每个比对项的输入都换了** ⇒ ⇒ ⇒ 所以：**表里不许有重复的比对项**；每轮之后拿 harness 的 `--list` 与记录里的 `[PASS]` 清单**逐条对账**（名字、地址、条数）⇒ ⇒ 这一步能同时抓出重复的比对项、漏记与错址。

⇒ 这两条与"量具侧的 ABI 错误会伪装成重建的数值差异"同族 ⇒ ⇒ 归到一条：**下"这是重建的缺陷"这个结论之前，先证明量具是新的、是对齐的。**

### 生成器自己的算术也跑在 `_PC_24` 下，而且"到达"不等于"有区分力"

两条同族的教训，都来自同一个生成器：

1. **生成器自己的算术也受环境控制字约束。** `SetFpEnv()` 把 x87 控制字设成 `_PC_24` 之后就**留在那儿** ⇒ ⇒ 生成器是在**两次调用之间**跑的 ⇒ ⇒ 它算的每个表达式也是 24 位 ⇒ ⇒ `1.0 + std::ldexp(1.0,-30)` 在生成器里**等于 1.0**（正是那个"精确对撞"最不能取的值）⇒ ⇒ 第一版对撞族因此**退化成随机**，变异检查照样全过 ⇒ ⇒ ⇒ **要特定位型就用位型构造**（`uint64_t` + `memcpy`），或者至少在环境控制字下验证一遍 ✓
2. **"能到达退化分支"不等于"有区分力"。** 一个 `bool` 比对项只有在两侧结果落进阈值一个 ulp 内时才翻转 ⇒ ⇒ 随机几何的操作数量级在千时命中率约 **10⁻¹⁰** ⇒ ⇒ 四个已转写的 `Intr*<double>::Test` 比对项**通过百万次也证明不了转写**（把分支退回 binary64 仍全过）⇒ ⇒ ⇒ **必须把两侧精确放到同一点**（如 `1+2⁻³⁰` 在 binary64 精确、24 位被舍成 1.0）⇒ ⇒ 变异后失配 ~50% ⇒ ⇒ 这时比对项才算见证 ✓

⇒ ⇒ 判据写死：**每个新比对项都要做双向变异检查**（退源码 → 比对项必须失败 → 恢复 → 比对项必须通过），并把**两个方向的计数**记下来 ⇒ ⇒ 只报"通过"的比对项，等于没测 ✓

### 比对项"通过"不等于重建正确，除非生成器能到达那个区间

`DistVector3Box3` 的平方距离缺陷在百万次抽样里只出现**一次**，因为生成器几乎撞不进 float 非规格化区间；而**刻意构造**该区间后，`DistVector2Box2` 与 `DistSegment3Segment3` 立刻各暴露一处同型缺陷（每百万 1.7 万次失配，差一个非规格化 ulp）。非规格化区间是 x87 指数范围这条"退化分支"的入口：float 的非规格化数装不下 24 位有效位，零售在 x87 栈上算完才落回 float，重建用 float 算就会差一个 ulp。

所以"比对项通过"只说明**生成器走到的地方**一致。写比对项时要问：这个函数的哪些区间是随机的抽样几乎到不了的？把它们构造出来。

### `-x` 必须是真正的 `fchs`，不是 `0 - x`

x87 的 `fchs` 对 **`+0.0` 给出 `-0.0`**，而 `0 - 0` 在同样精度下是 **`+0.0`** ⇒ ⇒ 二者**位型不同**，而比对项比的是原始位 ⇒ ⇒ 实例：`IntrSegment3Sphere3<double>::Find` 的第一个参数是 `-fA1 - root`，源码第一版写成"从零减" ⇒ ⇒ 比对项在 `fA1 == 0` 的抽样上失配 **100034/200000**，报的正是零售 `-0.0` vs 重建 `+0.0` ⇒ ⇒ ⇒ **凡是从指令里读到 `fchs` 的地方，重建里也要真的取负**（`X87Neg`），不要用减法表达 ✓

### "上游副本与零售不同"是结论，不是前提 —— 一条关于 `GenerateOrthonormalBasis` 的撤回

**曾记：** 零售的 `Vector3<double>::GenerateOrthonormalBasis`（`0x00A3D150`）是 **WM3.4 的四分支算法**，重建里是 **WM4 的两分支**，所以这是源码层面的算法差异；以及 `IntrLine3Capsule3<double>::Find`（`0x00A80080`）的 dot 分组是 `(y+z)+x` 而源码写 `(y+x)+z`。

**两条都撤回。** 机器码与副本都不支持：

* WM3.4 副本（`.tmp/wm3/Source/Math/Wm3Vector3.inl:604`，2004 年的只读文件）本身就是**两分支**：按 `|W.x| >= |W.y|` 分支、逆长度 `1/sqrt(z*z + x*x)`、`V = rkW.Cross(rkU)`；重建也是两分支；零售的**两个体**（double `0x00A3D150`、float `0x00A3CF80`）同样两分支：`fabs`/`fcompp`/`fnstsw`/`test ah,0x41`/`jp` 的判别、同样两个和、CRT 平方根 `0x00A91000` 之后 `fld1; fdivrp st(1)`。
* `IntrLine3Capsule3<double>::Find` 的三个点积都是 **`(y 项 + x 项) + z 项`**（两次 `faddp`：第一次合并 `dy` 与 `dx` 的两个乘积，第二次再加 `dz` 的乘积）⇒ ⇒ 与源码的 `(y+x)+z` **一致**。

**真正的差别是舍入，不是算法**：零售体是 x87 代码、引擎跑在 `_PC_24` 下 ⇒ 24 位有效位；重建的 double 分支原先是普通 binary64（53 位）⇒ ⇒ 已按机器码改成 x87 转写，两个比对项见证（退源码 **198173/200000**、恢复 0 ✓）。

⇒ ⇒ 教训：**"上游副本与零售不同"是结论，不是前提。** 这一条把副本当成了四分支算法的来源，而副本本身说的是两分支 ⇒ ⇒ **读副本要读到"分支数"这一层**，不能只对得上函数名 ✓ ⇒ ⇒ 而"double 体与 float 体分组不同"这种判断，同样要**逐条 `faddp`/`fsub` 对过**再说 ✓

⇒ ⇒ ⇒ 顺带记下一条**真正的**源码差异（这轮没改，留给后面）：重建的 `Vector3::Normalize<double>` 仍是 binary64，而且**零售的 `Normalize` 返回 `1/length` 而源码返回 `length`** ⇒ ⇒ 基函数的 `bUnitLengthW == false` 分支因此还不是零售的（两个比对项用的是 `bUnitLengthW = 1`，与零售自己的调用点一致）✓

### 判定"零售返回什么"必须把 x87 栈从入口追到 `RET`

`Vector3::Normalize` 的两个零售体（float `0x00452AF0`、double `0x00A3D0A0`）都被记成"零售返回 `1/length`" ⇒ ⇒ **错了，已撤回** ⇒ ⇒ 零售返回的是**长度**。错在两处栈语义：

* **`D8` 族写 `ST(0)` 且不弹栈** ⇒ ⇒ `FLD1; FDIV ST(1)` 之后 `ST(0)` 是**倒数**、`ST(1)` 是长度 ⇒ ⇒ 三个乘法消耗掉倒数的副本 ⇒ ⇒ 到 `RET` 时 `ST(0)` 剩下的是**长度**；
* **`FSTP ST(i)` 是先写后弹** ⇒ ⇒ `FSTP ST(1)` 把 `ST(0)` 写进 `ST(1)` 再弹 ⇒ ⇒ 弹完 `ST(0)` 又是那个**长度**。

⇒ ⇒ 教训：**"零售返回什么"只能靠追栈得出** —— 哪条写、哪条弹、哪条拷贝都要过一遍；只看算式（"它算了 `1/length`，所以返回 `1/length`"）会把**中间量**当成返回值 ⇒ ⇒ 而这类错误会以"语义缺陷"的样子出现，代价是改源码 ✓

⇒ ⇒ **旁证更快**：**先找零售自己的调用点**。`0x0050B829` 调 `0x00452AF0` 之后拿 `ST(0)` 与 `0.0` 比大小并 `jbe` ⇒ ⇒ 引擎的 `Normalize(&v) > 0.0f` 用的就是**长度** ⇒ ⇒ 判"返回什么"时，调用点比读体省事，而且不会读错栈 ✓

⇒ ⇒ ⇒ 顺带说明：这条的**真实**差别是舍入（double 体是 x87、`_PC_24` ⇒ 24 位），已按机器码转写，两个比对项见证（退源码 **185934/200000**、float 比对项把返回值改成倒数 **136482/200000**，恢复均为 0）✓

### 先用"引擎是否引用"筛掉不该做的工作

上面几条都是关于**怎么把一个函数配准**。但还有一步在它们之前：**这个函数值不值得配**。
库里 `float` / `double` 各写了 **140 个**显式实例化，而 `src/` 真正引用的只有
**float 20 个、double 4 个** ⇒ ⇒ 给引擎不引用的实例化配对**改不了引擎**，那不是工作 ✓

**判定方法**（三步，一次构建就能定案）：把某个实例化的**全部** `template WM3_ITEM
class X<T>;` 一起撤掉 → 重新构建 `main.vcxproj` → **链接通过**就说明引擎不引用它，
**链接失败**则未解析符号**直接点名**被引用的成员 ✓

**两种看起来能用、其实不能用的办法**：

* **`grep` 类名** —— 头文件、注释、库自己的显式实例化都会命中。`IntrBox3Sphere3<double>`
  就是这么"看起来在用"的，实际 `src/` 只用了 `IntrBox3Sphere3f` ✓
* **类里加 `static_assert`** —— 库写了显式实例化，**assert 在引擎用不用它的情况下都会触发**
  ⇒ ⇒ 我第一次探这个类型时就掉进去了，看到 `Wm3IntrBox3Sphere3.cpp:870` 的实例化上下文
  就以为"被用了"，其实那只是 `template WM3_ITEM class X<double>;` 那一行 ✓

⇒ ⇒ ⇒ **只有"撤掉实例化看能不能链接"才是判据**；失败时的未解析符号还是**免费的签名清单** ✓

**已经入表的比对项不撤**：逐位验证过、跑起来不花钱，而且 x87 方法就是从它们身上建立的。
停的是**继续往未使用的实例化上投工作** ⇒ ⇒ 所以每轮开工前，先问一句：**这个类的实例化，
引擎真的会执行吗？** 答案在 `reachable.md` 的 `engine uses` 列 ✓

### x87 状态字：C3 在"相等"和"无序"时都是 1，不是"大于"

`FUCOM` 之后 **C3=1 覆盖"相等"和"无序"两种情况**，C0/C2 才区分大小 ⇒ ⇒ 而
`test ah, imm` 之后的 `jne`/`je` 是**整数零标志**（"两个被测位都没置"），`jp`/`jnp` 是
**AND 结果的偶校验**（对两比特掩码就是"两个被测位相同"）⇒ ⇒ ⇒ 把 `FUCOM` 读成
"C3 表示大于"会把分支读反：`test ah,0x44; jnp` 是**相等**那支，不是大于 ✓

⇒ ⇒ 定极性要用**三态样本**（相等、大于、小于各一个），不能用两态样本 —— 我在
`Eigen::Tridiagonal3` 上从 `test ah,0x44` 推出"零售在 `fM02 > 0` 时进分支"，重做后
真实条件是 **`fM02 != 0`** ✓

### 零售的 Wild Magic 两个精度都是 x87 —— 所以 float 比对项通常不需要转写

零售的 **float 体也是 x87 代码**（`fld dword` / `fstp dword`），而 float 的 x87 运算
本身就是 24 位有效位 + **扩展指数** ⇒ ⇒ 与 SSE 重建版的差别**不在舍入、在指数范围**
⇒ ⇒ 只在值离开 float 正规范围时才显形 ⇒ ⇒ ⇒ 所以 float 比对项**一般不需要 x87 转写**，
需要的是**分支/次序对不对**（`Eigen<float>` 就是只改了一个分支、算术一字未动）✓

⇒ ⇒ 反过来，**double 体才是需要 `X87Asm` 转写的那一侧**（53 位操作数、乘积需 106 位）✓

### CRT 的平方根保留精度控制位 —— 所以它是 24 位的

`0x00AA7BD5`（CRT 平方根 `0x00A91000` 用的那段）算的是 **`(CW & 0x300) | 0x7F`**
—— 把**精度控制位掩出来保留**，只补其余位 ⇒ ⇒ 在引擎的 `_PC_24`（`0x007F`）下结果**还是
`0x007F`** ⇒ ⇒ **根是 24 位的**，不是 binary64 `sqrt` 给的 53 位 ✓

⇒ ⇒ 所以 double 路径里用 `Math<double>::Sqrt` 是错的（差不止一个 24 位 ulp）⇒ ⇒ 要用
**`Wm3Detail::X87Sqrt`**（取环境控制字）✓

⇒ ⇒ 顺带纠正两处旧账：`DistVector3Box3<double>` 那段散文曾写"它把控制字规范到 `0x027F`
所以根是 53 位" —— **错**；而 **harness 的横幅**打印的是零售静态初始化之后的 `0x027F`，
**不是比对项实际用的 `gControlWord`（`0x007F`）** ⇒ ⇒ 看到横幅 `x87 CW=0x027F` 不代表比对项跑在
53 位 ✓

### `tools/x87sim` 的两个边界（用它读体之前先知道）

* **`_addr()` 读不了 SIB 索引**：解码器把索引寄存器的**编号**放进 `MemOp.index`，而
  `_addr()` 拿它当**寄存器名**去查（`self.regs[mem.index]`）⇒ ⇒ 任何 `[eax + ecx*8]`
  形式的操作数都会 `KeyError`，而索引为 0（eax）时会**静默读成 0** ⇒ ⇒ 用寄存器索引
  数组的体，模拟器**跑不了**（我在 scratch 驱动里绕过去了，工具本身没改）✓
* **调用了别的零售函数的体跑不了**：模拟器没有 `call`/`ret`、没有整数 `cmp`/`jcc`、
  也没有 `FLDZ`/`FCOMPP` ⇒ ⇒ 要跑整段算法得在 scratch 驱动里补这些 ⇒ ⇒ 但**值得**：
  double `Eigen::Tridiagonal3` 就是这么跑出来、与 WM3.4 算法逐位对上的 ✓

### 会泄漏的零售体不能做成比对项

零售的 `ConvexHull2<double>` **每次构造泄漏约 3 KB**（`~3 KB/hull`，没有任何归还）⇒ ⇒ 一个比对项若每次迭代构造一次，会在**约 350000 次后**因 `bad_alloc`（C++ 异常 `0xE06D7363`）死掉，**每个种子都一样** ⇒ ⇒ 而症状看起来像"扫到一半崩了"，**不像缺陷** ✓

⇒ ⇒ **围着"会分配"的体建比对项之前，先量它的析构**：若有析构函数，就构造几十万次、盯进程内存 ⇒ ⇒ float 的比对项没暴露这个问题，因为 **float 实例化不泄漏** ✓

⇒ ⇒ 泄漏点不在 hull 的析构函数（double `0x00A74BA0` 与 float `0x00A74970` 结构相同、都不销毁 hull 容器），而在 double 实例化分配用的某个 helper 里（`Mapper2`/`Query2Int64` 的 double 路径）✓

### thunk 里压 double 要"写进预留位"，不能"push 两次"

`sub esp,8` 之后再 `push` 两次，会把**预留的那 8 字节夹在两半之间**，被调方就把预留的垃圾读成一个参数、把下一个参数读成另一个 ⇒ ⇒ 症状是**被调方深处空指针**，完全看不出是 thunk 的问题 ✓

⇒ ⇒ 正确写法：`sub esp,8` 与 `push` 之间用 `mov dword ptr [esp+0], ...` / `[esp+4], ...` 把两半**写进预留位** ✓

### 零售的 double 类与 float 类**成员偏移也不同**

不只 vtable 槽位不对齐（那条已有），**成员也不在同一偏移**：`ConvexHull` 基类的 `m_eQueryType` 从 `+0x04` 挪到 `+0x08`、`m_fEpsilon` 从 `+0x18` 到 `+0x20`、`m_bOwner` 从 `+0x1C` 到 `+0x28`；派生类把 `Query3` **内嵌**在 `+0xB8`（float 是指针）；平面数据在 `+0x70`/`+0x88`（float 是 `+0x44`/`+0x50`）⇒ ⇒ ⇒ **读 double 实例化的构造器，不要把 float 的偏移平移过去** ✓

### 同一份源码在零售里可以编成两个不同的体

WM3.8 的 `Vector3.cpp` 里 **`Length`（`0x00452A90`）是 SSE 体**，而
**`SquaredLength`（`0x004757E0`）是 x87 体** ⇒ ⇒ 两者在 float 正规范围内一致，
**在平方项非规格化处分道**（SSE 的平方按 binary32，x87 保留扩展指数）✓

重建把后者折进了前者（`Length()` = `Sqrt(SquaredLength())`）—— **WM3.4 副本也是这么写的**
⇒ ⇒ ⇒ **副本在这一点上跟着错**，只有零售机器码能定案 ✓ ⇒ ⇒ **副本可能是错的版本**：
先看零售的体，再信副本的形状，最后让比对项裁决 ✓

⇒ ⇒ 修正在共享模板里 ⇒ **能到达引擎**（`CAiSteeringImpl.cpp:198`、`:1458`）⇒ ⇒ 变异后
**529/200000** 失配，恢复后 0 ✓

### 成员"被引擎调用"与"零售里有独立体"是两件事

`Vector3<float>::Length` 被引擎调用，但零售的引擎代码**把它内联了** ⇒ ⇒ `0x00452A90`
在零售镜像里**一个调用者都没有** ⇒ ⇒ 这样的比对项仍然值得有（它钉住的是引擎内联副本依赖的
那个值），但 **"缺体"和"死体"是两种不同的发现** ⇒ ⇒ 可达性判定要**做到成员级**：

* `Vector2<float>::Normalize()`：14 处引擎调用，但零售**没有它的独立体**（只有内联器留下的
  尾巴 `0x00452C80`，参数是长度和向量）⇒ ⇒ **既无体也无比对项** ✓
* `Zero()`/`NaN()`/`IsntNaN()`/`IsInvalid()`/`Compare()`/`DistanceSq*()`/`Sub()`/`PerpDot()`：
  **重建侧新增**，WM3.4 副本里没有这些名字 ⇒ ⇒ 拿重建比自己，不是配对 ✓
* `ZERO`：零售里是**静态数据对象**（`0x00F3D21C`），不是体 ⇒ ⇒ 比对项永远不可能失败 ✓

⇒ ⇒ 所以"`Vector3` 有 90 个符号"要读成 **"一个被内联到 90 处使用的体"**，不是 90 个体 ✓

### 零售的 float 体不都是 x87

`Length` 是 SSE，`SquaredLength`/`Dot`/`Normalize` 是 x87 ⇒ ⇒ "零售 float 体是 x87"
是有用的**默认**，不是**规则** ✓ ⇒ ⇒ 而"float 的 x87 运算在 float 范围内就等于 float 运算"
这句要补上反半边：**SSE 的 float 体不是 x87 体**，两者**恰好在非规格化边界上分道** ——
而那正是生成器magnitude 族所在的地方 ✓

**"有比对项"和"被执行"是两个独立的轴。** 之前的"引擎执行的 float 类"清单是**从有比对项的类推出来的**，

### "重建里有这个成员"不等于"零售里有这个成员"

`Wm3::IVector2<int>::operator<` 在重建版的 Debug 镜像里，零售也**有这个类**（RTTI 里有
`.?AV?$IVector2@H@Wm3@@`）—— 但零售的引擎**把比较内联掉了**：构建结构映射的下界查找
`0x005808D0` 本身就是那次比较（先 x 后 y、有符号），而**零售镜像里没有一处独立的双分量
整数比较**（全镜像只有 CRT 的 `memcmp` 在 `0x00A9185E`）⇒ ⇒ **没有体可配** ⇒ ⇒
对着重建自己的副本建比对项，等于**拿重建比重建** ✓

⇒ ⇒ **判定办法：在零售里找"体的形状"（偏移 0 与 4 处的两次整数比较），不是找名字** ✓

### 零售引擎按名字调用的成员，在零售里必然是 public

`Vector3<float>::CompareArrays` 在 WM3.4 副本里是 **private**（重建照抄成 private），
而零售是 **public** —— 因为**零售的引擎直接按名字调它**（`0x004F0A50`）⇒ ⇒
**访问说明符是重建的一部分**，不是无关紧要的装饰 ✓

⇒ ⇒ 而"这个改动不会影响引擎"的证明**是 `.text` 段的哈希，不是 diff 里没东西**：
`main.exe` 的 `.text` 在改前改后都是 `ed96fca73b7b5be547c2342fe5b02ccc` ⇒ ⇒
二进制被重新链接（md5 与 PE 时间戳都变了）但**一个字节的代码都没动** ✓

⚠ 但要注意：**我们的引擎并不调这个成员** —— `src/` 里只有注释提到它
（`VTransform.h:111`）。所以 public 不是引擎编译所必需，而是**harness 需要**（它
链接同一份头文件并直接调用）。**重建访问说明符的理由是"零售就是这样"，不是"引擎需要"** ✓

### `memcmp` 的返回值是**符号**，不是字节差

标准只保证 `<0 / 0 / >0`，而 MSVC 的实现**返回 -1 / 0 / +1** —— 实测：`msvcrt.dll`
与 `ucrtbase.dll` 对 `{0x00}` vs `{0x40}` 都返回 **-1**；用本项目自己的工具链
`/O2 /Oi /MD` 编译的探针，`00|40`→-1、`40|00`→+1、`02|00`→+1 ✓

⇒ ⇒ 所以"零售内联的 memcmp 返回 -1/0/+1，而 CRT 的 `memcmp` 返回字节差"这句话是**错的**
—— 这一轮我把它写进了比对项描述和 README，事后才测出来，只能回头改成"两边都返回 -1/0/+1，
这个比对项证的是**逐位比较与通道顺序**，不是归一化方式" ✓

⇒ ⇒ 教益：**"某个库函数返回什么"要测，不要按记忆写**；尤其当这条断言是用来解释
"这个比对项为什么有区分力"的时候 —— 说错了，读者会以为它证了它其实没证的东西 ✓



### `reachable.md` 是生成物，手改的内容会被覆盖

下一次重新生成就没了** —— 这一轮就发生过一次：手工加进去的"为什么比对项数与函数数不同"
那一节，写进文件、提交、然后被一次重新生成抹掉，事后只能从 git 里捞回来再补进脚本 ✓

⇒ ⇒ 要改 `reachable.md`，**改生成脚本**，再重新生成 ✓

### "类被执行"不等于"这个成员被执行"

普查里有一轮把 44 个成员判成"可配对"，依据只是**它们的类被执行**——note 里引的
`C6`/`C20` 这种编号只存在于当轮的草稿里，仓库里没有图例，等于没有证据 ✓

⇒ ⇒ 一个成员要判成**可配对**，必须**两半都成立**：`src/` 里**点名这个成员**的调用点
（同类另一个成员的调用点不算），以及零售里能指出地址的独立体 ✓

⇒ ⇒ 引擎执行、但零售**没有独立体**的（`Quaternion<float>::Rotate` 就是），判 `不适用`
并写明 "executed but no retail counterpart" —— 那是**结论**，不是缺口 ✓

### "零售没有这个体"必须写明看过哪里

否则它只是一句断言。这一轮读过的三个范围要留在记录里：零售的 `Vector3.cpp` 块
`0x004F0800`–`0x004F0A50` 只有 `CompareArrays`（`0x004F0A50`）和 `operator==` 包装
（`0x004F08B0`）；`Quaternion.cpp` 块 `0x004F0800`–`0x004F0C10` 只有 `CompareArrays`
（`0x004F0B40`）和 `operator==` 包装（`0x004F08E0`）；而**整个 WM3 区
`0x00A00000`–`0x00A90000` 里没有一处体的乘法达到六个**——一个旋转矩阵要十八个 ✓

⇒ ⇒ 反过来说：**"有体"也是查出来的**，`Vector3<float>::operator==` 在 `0x004F08B0`
就是这一轮从同一块里找出来的，而旧普查把它记成了"引擎只用 `!=`" ✓

### 编译器发射的成员体保留**代码**，不保证保留**调用约定**

`Quaternion<float>::CompareArrays` 在源码里是普通 thiscall，但编译器在 `0x004F0B40`
发射的那份**从 EAX 取实参**、以裸 `ret` 返回——它没有读 `[esp+4]` ✓

⇒ ⇒ **写 thunk 之前先读第一条取参指令和结尾**，不要因为"别的成员都是压栈"就默认压栈：
压进去的实参不会被弹掉，返回地址就错位了 ✓

⇒ ⇒ 调用目标也不能放 `EAX`（那里正装着实参）——用 **`EDX`** ✓

### `bool` 比对项要瞄准**比较语义**，不是瞄准算术

逐位比较的判别样本是"同一份位型里放一个 NaN"和"某一路 `+0.0f` 对 `-0.0f`"——而后者
**必须让其余通道完全相同**才有效：两侧随机时，分量式 `==` 本来就会答"不等"，这个样本
根本不触发 ✓

⇒ ⇒ 这一处修改把 `Vector3<float>::operator==` 的变异失败数从 **20109** 抬到 **49845** ✓

### 建一整批之前，先建一个，问这一批到底**能不能**有区分力

构造函数比对项比的是**对象字节**，而在这套库里那通常意味着比**引用存下的地址**、比**没人
初始化的字段**。三个试点：两个败在根本原因（对象里存引用、基类字段根本没写），一个败在
**判错了问题** ✓

⇒ ⇒ 第三个是 `Sphere3<float>(Vector3, float)`：试点看到"引擎自己的构造点 `0x005D38CA`
被内联"，就判"零售没有体"。但**"这个调用点被内联"与"别处有没有体"是两个问题**——
`0x004740C0` 就是它的体（`ECX`=对象、`[esp+4]`=Vector3*、`[esp+8]`=半径、`RET 8`）✓

⇒ ⇒ 所以**先确认"有没有体"，再谈"能不能建"**：否定判断比肯定判断更容易出错，而它恰好会
把整个类别静默地划掉 ✓

⇒ ⇒ 反面教材也要记住：`ContAlignedBox` 抓到"重建没写 axis"确实靠的是对象字节，但它是
**函数**比对项（按值返回一个 box），不是构造函数——判据要落在"这些字节有没有确定值"上，
不是落在"是不是构造函数"上 ✓

### 零售的构造函数约定与源码不同：`ECX` 可能是**隐藏返回指针**

`DistVector3Box3<float>` 的构造函数在 `0x00A45730`：`ECX` 就是**对象本身**（不是 `this`
供成员访问那么单纯），两个实参在栈上，结尾 `RET 8`；同一个文件里的其它成员却是
`ECX = this` + 一个栈实参 ✓

⇒ ⇒ 写 thunk 前先看**结尾弹几个字节**和**第一条取参指令**，别照抄同类成员 ✓

### 构造函数约定不是源码的约定，cdecl 的压栈顺序也不是你读到的顺序

`Sphere3<float>` 的构造函数：**`ECX` 是隐藏返回指针**（对象本身），中心地址在 `[esp+4]`、
半径在 `[esp+8]`，结尾 `RET 8` ✓

⇒ ⇒ **cdecl 从右往左压栈，最后压的那个落在最低地址** —— 中心必须**最后**压。搞反了会在
零售体的第一条 `fld [ecx]` 上崩，而 harness 报的是 crash、不是 mismatch ✓

### 缩小比较范围靠 `outWords`，不是靠掩码；而"排掉噪声"不等于"还有东西可比"

harness 只比较输出缓冲区的 `outWords` 个字，所以比对项**只写它要比的那几个字**即可 ✓

⇒ ⇒ `Intersector` 的 vptr 因此可以跳过（写到 `+0` 之后不写它），但剩下的两个词是
`m_fContactTime = 0.0` 和 `IT_EMPTY = 0` —— **两边永远是常量** ⇒ ⇒ 这个比对项**不可能失败**，
那它就不是比对项 ✓

## 不要为了让比对通过而改编译选项

**这条是硬规则，不要绕过。** 不得修改 `main.vcxproj`、`build.bat` 或任何
`.props` 里的编译选项（`/arch:`、`/fp:`、`/Oi`、`/O2` 等），哪怕只是为了做一次
实验、哪怕只改一行。

重建的目标就是按它现在的方式编译。零售二进制与重建版逐位不一致时，**那本身就是
结果**，harness 的职责是报出来，而不是打开一个开关把两边凑齐。

这个诱惑是能量化的，所以特别容易破例：`dependencies/WildMagic3p8/wmdiff` 实测，
加上 `/arch:IA32`（强制 x87）能让 `Vec3::LengthSq` 从 575 次失配变成 200000/200000
全等 —— 正因如此才禁止。那个开关不会让重建更正确，只会让重建变成另一个程序。

差异的修复位置只能是重建源码，或比对中零售一侧的接线，绝不在“怎么编译”上。

**唯一例外是"让量具与树编译成同一个程序"**：一致性模式统一属于这一类——它改的是**保真度**，不是"把两边凑齐"。判据是：**改完必须全量重测**（wmdiff 全表 + 引擎构建 + lockstep 对局），且**比对项与比对项之间的差异不得因此改变**；若有任何一个比对项动了，那就是在掩盖差异，不是在修保真度。

详见 `dependencies/WildMagic3p8/wmdiff/README.md` 的 `## Rules` 与
`## Floating-point codegen is per function, not per build`。

## 编译器版本差异是客观条件，我们只还原行为

零售版由 2007 年的 MSVC 生成，本重建由 MSVC 14.38/14.44 生成。**不打算回到零售版的
编译器**，也不应该把这个差距当成待修的缺陷 —— 我们要做的是在当前工具链下还原**行为**，
不是复刻另一个编译器恰好吐出的那些位。

因此 `wmdiff` 的 FAIL 不自动等于 bug，要分三档看：

- **PASS** —— 零售与重建逐位一致，无需处理
- **已知差异** —— 不一致，但机制已查明（求和顺序、双重舍入、非规格化处理等），
  记录后跳过
- **机制不明** —— 不一致且没人查清原因。**只有这一档是真正的工作量所在**

一个重建的 bug 会藏在第三档里，和代码生成差异混在一起，直到有人把两边函数体都 dump
出来才能分辨。所以别把第二档当成待办清单，也别把第一档当成唯一目标。

注意第二档是否影响对局，是另一个问题，`wmdiff` 回答不了：1 ULP 的点积差是真实的行为差，
也可能正是 lockstep 模拟会放大成 desync 的那类差异 —— 取决于游戏实际走到哪些函数。

改编译选项一律禁止，见上一节。

## 判定标准：与零售逐位一致

**与零售二进制行为完全相同，是重建正确性的最主要证明，也是唯一标准。** 同一批输入下，
重建侧与零售侧产出相同的位，这个比对项才算过。

**查清失配原因只是准备工作，不等于可以放行。** 知道 `Vec3::Dot` 是求和顺序问题，
只说明该往哪个方向试，不说明它离通过更近了一步。**FAIL 的比对项在通过之前一直是未完成项。**
不要把失配的比对项分成"已知"和"不明"两类，然后把第一类当成做完了 —— 从外面看，重建的 bug
和代码生成差异长得一模一样，只有把差距填平才能分辨。

编译器版本差距是真实约束，不是理由。零售由 2007 年的 MSVC 生成，本重建由 14.38/14.44
生成，不打算回到零售版编译器 —— 这意味着**唯一的收敛位置是重建源码**：把表达式写成
让当前编译器发出与零售相同的指令。某个差异确实无法这样收敛时，要明确写出来并附上机制，
命名为永久限制；**不许悄悄提升成"可接受"。**

失配时还有一处可以改，但不是重建本身：harness 对零售运行环境的**保真度**。零售在特定的
x87 控制字与 MXCSR 下执行，如果重建侧跑在不同的 FP 标志下，这个比对测的根本不是它声称
的东西。把环境调对是拿到正确答案的一部分；改重建的编译方式不是，见上一节。

当前三个失配的比对项的处理方向：

- `Vec3::Dot`（14.3%）—— 纯顺序问题，**看起来可以在源码里收敛**：把求和写成
  `Z*Z + Y*Y + X*X`，应能让本编译器发出零售的顺序。待做并复测。
- `Math::InvSqrt`（12.5%）—— 零售全程 64 位中间量、最后舍入一次。先测清本编译器对
  `(Real)(1.0/sqrt((double)x))` 实际是按 float 还是按 double 算的，再决定怎么写。
- `Vec3::LengthSq`（0.29%）—— 样本全在非规格化区间。在对重建下任何结论之前，先确认
  harness 是否按零售真实的 FP 标志在跑（banner 报的 MXCSR 与 `main.cpp` 里的常量本来就不符）。

## x87 模拟器（tools/x87sim）

`tools/x87sim/` 是 32 位 x87 FPU 的模拟器，用来逐位复现零售的浮点行为。
包里只有模拟器（`x87sim/`）和硬件参照（`hwprobe/`），**不含**零售字节比对、
抽样语料或包内测试代码 —— 那些属于调用方。

- 跑指令级测试（会按需编译硬件参照，编译失败即报错，不跳过）：

```bash
python -m unittest discover -s tools/x87sim/tests
```

- 当模拟器抛出 `Stop('unhandled x87 %02X %02X')`：先用
  `tools/x87sim/hwprobe/build.py` 构建，再用
  `tools/x87sim/hwprobe/build/x87ref32.exe` 量那一条编码（装入六个已知值、
  执行、dump 寄存器文件），把量到的语义写进 `x87sim/decode.py`，
  再补一条指令级测试。硬件只接受一部分编码，其余是无效指令，
  模拟器应当继续抛 `Stop`。
- 精度模型：`SIMPREC` 选控制字精度 —— `53` 时寄存器保留 53 位有效位、落盘才
  舍入到 float32；`24` 时每次运算都舍入到 float32。**引擎跑在 `_PC_24`
  （`fninit; fldcw 0x007F`）下，所以引擎的浮点链用 `24`**；`53` 是环境控制字
  `0x027F` 下的行为。别在 `_PC_24` 下按 53 位去量零售：重建自己的 `double` 链
  会让 MSVC 发出一条 `fldcw` 把控制字重置，于是量到的是另一个函数
  （`dependencies/WildMagic3p8/wmdiff/README.md` 的 "The swept rows, closed"
  撤回了这个结论）。除法只舍入一次（从精确有理数），不能先舍入到 double 再
  舍入到 float32。
- 详见 `tools/x87sim/README.md`（含已知坑：寄存器组是物理带旋转栈顶的、
  `FSTP ST(i)` 先写后弹、部分编码在硬件上根本不存在、`DD E0+i` 是
  FUCOM 而不是减法、DC 族的内存操作数是 64 位等）。
