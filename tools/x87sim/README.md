# x87sim

A simulator for the 32-bit x87 FPU, and the hardware reference that
keeps it honest.

The simulator exists because the reconstruction has to reproduce the
retail's floating point *bit for bit*, and the retail's x87 behaves in
ways the manuals do not describe: the D8/DC/DE families differ in
destination register and pop behaviour, some encodings do not exist at
all, and a division has to be rounded exactly once.  A simulator that
guesses is worse than no simulator, so every rule in here was measured
on the machine with `hwprobe/x87ref32.exe`.

The tool has two halves:

* `x87sim/` - the simulator (a library, no test code, no corpus);
* `hwprobe/` - the reference: a small C program that executes one x87
  encoding on the real CPU and dumps what it left behind.

## Layout

```
tools/x87sim/
├─ README.md              this file
├─ x87sim/                the simulator package - NO test code, NO corpus
│  ├─ __init__.py
│  ├─ decode.py           opcode+modrm -> semantics
│  ├─ cpu.py              the 8-register x87 file, rotating top, status word
│  ├─ memory.py           byte-addressed memory + ESP-relative spill slots
│  ├─ arithmetic.py       exact rationals + single rounding
│  └─ machine.py          the interpreter loop and the public entry points
├─ hwprobe/               the hardware reference (C)
│  ├─ x87ref32.c          run one encoding or a byte blob on a real CPU
│  └─ build.py            Python build script (cl.exe, x86; no .bat chaining)
└─ tests/                 instruction-level tests ONLY
   └─ test_instructions.py
```

## Running the tests

```bash
cd D:/D/BC/2026/faf-re
python -m unittest discover -s tools/x87sim/tests
```

The test builds the hardware reference on demand (`hwprobe/build.py`
rebuilds it when the executable is missing or older than the source)
and compares the simulator against the real CPU for every encoding the
decoder implements.  If the reference cannot be built the tests fail -
they are never skipped.  The tests need no retail binary and no corpus:
the inputs are generated by the test itself.

The build is x86 on purpose: the x87 semantics have to be measured in
32-bit mode, which is the mode the retail runs in.  `build.py` locates
`vcvarsamd64_x86.bat` (Visual Studio 2022 is on `G:` on this machine,
not on `C:`), writes the cmd semantics into a temporary `.bat` and runs
that - nested quotes in an interactive `cmd` do not survive.

## Using the simulator as a library

There is nothing to install.  From a caller in another directory, put
the package on the path with a path relative to the caller's own file:

```python
import os
import sys

sys.path.insert(0, os.path.join(os.path.dirname(os.path.abspath(__file__)),
                                '..', '..', 'tools', 'x87sim'))

from x87sim import Machine, run_function
```

`run_function(code, base, mem=None, reg=None, mem64=None)` runs a block
of machine code at virtual address `base` until it returns, and returns
the machine; `machine.result` holds what was in ST(0) at the `ret`.
`mem` is a `{address: value}` mapping of 32-bit float slots, `mem64` one
of 64-bit double slots, `reg` a `{register: value}` mapping.

For a caller that wants to step instead of run:

```python
m = Machine(mem=mem, reg=reg, code=code, base=base)
while True:
    pc = m.step(pc)
    if pc is None:
        break
```

The FPU state is `m.st` (the eight-register file with its rotating top,
`m.st.s(i)` is ST(i) and `m.st.top` is the top), the condition codes
are `m.c0`, `m.c2`, `m.c3`, and `m.status_word()` is the status word
the way the hardware has it.

## The precision model

`SIMPREC` selects the precision the control word has:

* `SIMPREC=53` (what the retail's chain needs): the registers keep
  53-bit significands, and only the spills to memory are rounded to
  float32.
* `SIMPREC=24`: every operation is rounded to a 24-bit significand
  (float32), which is what the x87 does under the `_PC_24` control
  word.

A division is rounded **once**, from the exact rational, never through
a double: rounding to double and then to float32 is two roundings and
can land one ulp away.  `arithmetic.py` keeps the quotients as
`Fraction`s for that reason.

The reference runs with the control word 0x127F: 53-bit precision,
round to nearest, affine infinity - the IEEE-like behaviour the
simulator models.

## Known pitfalls

These are the things that cost the most time to get right.  They are
properties of the hardware, and the simulator models them.

* **The decode comes from the raw opcode and ModRM bytes**, never from
  a disassembler's text.  The D8, DC and DE families differ in
  destination register and pop behaviour, and the SDM's "pop" column is
  wrong for some of the D8 forms: they write ST(0) and do *not* pop.
* **`FSTP ST(i)` stores ST(0) into ST(i) and *then* pops.**  The order
  matters, because the value that ends up on top is the one that was
  just written.
* **The register file is physical with a rotating top.**  ST(i) is
  `R[(top + i) & 7]`, and the file keeps its contents when a register
  is popped.  The compiler relies on being able to read ST(i) past the
  live depth (`fmul st(4)` with a depth of 4).
* **A register that was never written, or that was popped, holds the
  indefinite value on the hardware** (a quiet NaN), so a comparison
  against one is unordered and an arithmetic operation on one raises
  the invalid operation exception.  The simulator keeps the stale
  contents of the physical file there instead - that is what the
  compiler relies on - so the instruction level test does not compare
  the condition codes of an instruction that uses such a register.
* **`fnstsw ax` leaves the condition codes in AH, and the retail then
  does `test ah, imm`**: the branches look at the *integer* flags that
  TEST sets (ZF from the AND result, PF from its parity), not at the
  FPU's C0 bit.  The simulator keeps the same split.
* **Not every encoding the manuals mention exists.**  The x87 decoder
  only accepts a subset: `FST ST(i)` exists for i = 0 only, `FCOMPP` is
  `DE D9` only, `DD F0+i` and `DB F8+i` do not exist at all, and the
  D9 special functions are only the ones the SDM lists.  The others
  raise an invalid instruction exception, and the simulator raises
  `Stop` for them.
* **The DB family does not do what the manuals say on this hardware.**
  Measured: `DB C0+i .. DB D8+i` copy ST(i) into ST(0) without
  pushing, the arithmetic forms (`DB E0+i`, `DB E8+i`, `DB F0+i`) do
  nothing, and the memory forms load integers and store zero.  The
  copy is implemented (it is consistent and measurable); the rest is
  left unimplemented rather than guessed at.  The retail never uses
  the DB family.
* **The DC family's memory forms read a 64-bit double** on this
  hardware, not a 32-bit float.
* **`DD E0+i` and `DD E8+i` are the unordered comparisons FUCOM and
  FUCOMP**, not subtractions.
* **`FFREE` empties the register**: reading it afterwards gives the
  indefinite value.

## The extension workflow

When the simulator raises `Stop('unhandled x87 %02X %02X')`, it is
telling you the opcode and the ModRM byte it did not know.  To add
that instruction:

1. **Measure it.**  `hwprobe/x87ref32.exe` executes one encoding on
   the real CPU:

   ```bash
   cd tools/x87sim/hwprobe/build
   ./x87ref32.exe op <op> <reg> <rm> --st <6x float32 hex> [--mem <hex blob>]
   ./x87ref32.exe blob <hex bytes>     --st <6x float32 hex> [--mem <hex blob>]
   ```

   `<op>` is the escape byte in hex (`d8`, `d9`, `db`, `dc`, `dd`, `de`,
   `df`), `<reg>` and `<rm>` are decimal and select the ModRM fields.
   `--st` is six float32 bit patterns (8 hex digits each), loaded in
   order, so the last one ends up in ST0.  `--mem` is a blob of bytes;
   it is placed in a buffer whose address is printed as `MEMBASE`, and
   EBX is set to that address, so a blob can address it with
   `[ebx+disp]`.

   The program prints the control word, the status word, the stack
   top, ST0..ST7 and the memory blob.  Six values are loaded, so
   ST0..ST5 are known and distinct; the instruction runs; then the
   whole file is dumped.  A form that pops one shifts the window by
   one, a form that pops two by two, which reveals both the
   destination and the pop behaviour.

   Use the `blob` mode when the encoding is not a plain register form
   (a memory form, for instance), and `X87REF_LOADS` to change how
   many of the six values are loaded.

2. **Write the measured semantics into `x87sim/decode.py`.**  The
   register forms live in `_REG_TABLE`, the memory forms in
   `_MEM_TABLE`.  An `X87Op` says what the instruction does: the
   destination (`st0`, `sti`, `mem`), the source (`st0`, `sti`, `st1`,
   `mem`), the operation (`add`, `mul`, `sub`, `rsub`, `div`, `rdiv`,
   `cmp`, `copy`, `free`, `neg`, `abs`, `one`), how many registers it
   pops and whether it pushes.  A table entry also lists the `rm`
   values the hardware accepts - an encoding outside that set is an
   invalid instruction, and the decoder raises `Stop` for it.

3. **Add a matching instruction-level test.**  The tests are generated
   from `decode.implemented()`, so a new entry in the table becomes a
   new test automatically.  If the instruction is not modelled by the
   table (an encoding the hardware rejects), leave it out: the decoder
   should raise `Stop` for it.

## The retail binary is not needed here

The tool's own tests are self-contained: the inputs are generated, the
reference is built from source, and nothing in `tools/x87sim/` refers
to the retail executable, to a probe dump or to a corpus of draws.
Using the simulator *on* the retail is the caller's business, not the
tool's.
